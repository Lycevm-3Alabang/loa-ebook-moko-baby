### S2 — what the investigation changed

- The plan's S2 had two halves. The scan found **both states are unreachable**: the FKs cascade
  (`rubric_groups → rubric_categories → rubric_items → evaluation_ratings`, all `ON DELETE
  CASCADE`), so a rating cannot outlive its rubric item; and a period has **one** rubric group with
  the category name resolved at read time, so the two alias spellings never coexist in one period's
  figures.
- So the slice landed as the **narrow fix** (the owner's choice): the general rating leaves the
  error bucket out, and the reachable numbers **do not change** (the bucket cannot exist).
- ⭐ **The reachable question the old item never asked** — a criterion the app has **no column for**
  (a school adds a category like "Course Coverage") **is a real criterion**: it counts toward the
  general rating today and no column shows it. That behaviour is **kept**; changing it is a product
  decision, and it is recorded in `TODO.md` rather than decided here.
- The **alias half** was **not** changed: pooling the two spellings exactly needs the per-category
  counts, which the column mapping does not have — a ripple through every caller to fix a state
  the schema forbids. The map stays as the defensive lookup it was written to be.

### S1 — what the investigation changed

- The plan's blast radius for option A said "2 write sites". It is **3**: the restore has to bring the
  state back with the flag, or a restored response would stay out of every figure.

## Decisions

### The story is eight independent stories

The scan (below) shows the eight groups share **no** code, **no** invariant and **no** test file
except through two shared contracts. They are not one change; they are eight, and three of them
are **product decisions** the code cannot make. The plan therefore has to be a **sequence of
independent slices**, each with its own decision, not one edit.

### How each `applies` invariant is preserved (for every group)

- **API routes stay thin** — `app/api/` — **applies** where a route is touched (the drill-down and
  the faculty page are routes): they keep parsing, delegating and returning JSON; the decision
  lives in the repository or the service, not in the route.
- **proxy.ts is the access-enforcement point** — `proxy.ts` — **n/a**: no route, page or role change
  in any of the eight.
- **All Supabase access goes through repositories wired by DI** — `lib/repositories/factory.ts` —
  **applies** where a read or a write changes: the filters move into the repository methods.
- **Double-click prevention via SubmitButton** — `components/ui` — **n/a**: read-only surfaces, and
  the one write path (the admin's invalidate button) is already a form.
- **Role is pipe-delimited; priority ADMIN > DEAN > FACULTY > STUDENT** — `lib/utils/roles.ts` —
  **n/a**: no role logic touched.

### The layering order (the repository contract's order)

Route → Controller → Service → Repository → Supabase. For the read groups the change lands in the
**repository** (the filters), for the display groups in the **component**, and for the deletions in
the **repository + the interface + the tests**. The `exec_sql` group lands in the **schema + the
service**, and the font group in the **layout + the assets**.

### The gold paths to read first

`features/`, `app/api/`, `lib/repositories/factory.ts`, `lib/evaluation-utils.ts`,
`lib/db/common.ts`, `proxy.ts`, `lib/auth.ts`.

### The proof command

`npm test` (the Tests line in `repository.md`). The repo's full gate, the owner's run:
`npx tsc --noEmit` → `npm run lint` → `npx vitest run` → `npm run build`.

**Teach — why the same number is on two screens.** `isDisabled` is a *flag*; `status` is a *state*.
Every surface filters the state (`status = 'SUBMITTED'`), and only some filter the flag. A
response invalidated through the admin's button or through the stale-mapping path carries the flag
alone, so it survives the state filter and is averaged in. The surfaces disagree because each one
asks a slightly different question of the row — and the report (2026-10-21) joined the list's
question, which widened the gap rather than closing it. The fix is one of two shapes: **filter
everywhere** (add `.eq("isDisabled", false)` to the two reads that lack it) or **make the flag mean
what it says** (the two flag-only writers also set `status = 'INVALID'`, so every surface's
existing state filter excludes them, and the "Invalidated" page still lists them because it reads
the flag). The second is one line per writer and touches no read.

### S1 — `isDisabled`: the same response counted on one page and not on another

**Problem.** `isDisabled` is a *flag*; `status` is a *state*. Every surface filters the state; only
the list and the report filter the flag. Two writers set the flag alone — `bulkDisableByPeriod`
(`features/evaluations/evaluations.repository.ts:358`, the admin's "Invalidate Result") and the
stale-mapping path in `findPending` (`:169`, `:207`) — so those rows survive every surface's
`status = 'SUBMITTED'` filter and are averaged into the drill-down's and the faculty page's figures.

| | Option | Blast radius | Proof |
|---|---|---|---|
| **A (rec.)** | the two flag-only writers also set `status = 'INVALID'` | 2 write sites; **no read changes**; the "Invalidated" page still lists the rows (it reads the flag); the coverage page's bucket is unchanged (it already treats a disabled submission as **disputed**) | the two writer tests + a new case: a bulk-invalidated response is excluded from the drill-down's figures |
| B | add `.eq("isDisabled", false)` to the drill-down's and the faculty page's reads | 2 reads; the flag then means "was invalidated", not "does not count" | the same + a parity case |
| C | leave it; document the difference | nothing | none |

### S2 — the category arithmetic: the `""` bucket **and** the aliases (one slice, one file)

**Problem.** A rating whose `itemId` no longer resolves becomes the category name `""`
(`lib/db/common.ts:99-110`). `computeGeneralRating` averages over **every** name present → the `""`
bucket **counts**; `mapCategoryAveragesToColumns` drops unknown names → it can **never** be a
Highest or Lowest Rubric. And `CATEGORY_NAMES` maps **two** spellings to one column; the loop
**assigns**, so the second **overwrites** the first — and which one wins depends on the database's
row order, so one subject can print two different numbers on two screens.

| Sub-decision | Option | Blast radius |
|---|---|---|
| the `""` bucket | **(a) rec.** — exclude unmapped names from `computeGeneralRating`: the average is over the 8 real criteria, which is what the columns show | the numbers change on every surface **where an item was deleted** (today: unknown — no surface shows it) |
| | (b) keep them and surface the count | a new field on every figure |
| | (c) treat an unresolvable `itemId` as a data error and log it | a log line; the number stays |
| the aliases | **(a) rec.** — average the aliased categories into one column | **a no-op on the current data** (the seed only uses the long spellings) |
| | (b) drop the aliases → an alias spelling becomes an unmapped name → the `""` rule above | worse |
| | (c) normalise the spelling in the database | a data migration + the map stays the fallback |

**Proof:** `lib/__tests__/evaluation-utils.test.ts` + `lib/__tests__/db-common-ratings-paging.test.ts`.

### S3 — the membership gate: the drill-down drops evaluations the faculty page keeps

**Problem.** The drill-down's evaluation set is the **term's roster**

faculty page and dropped by the drill-down**. The home-department half is intentional (contract
§3.15/§3.16); only the **semester** half is accidental — **and it has no test**.

| | Option | Blast radius |

| B | the faculty page also scopes to the period's semester | the faculty page's numbers change |
| C | the admin page stops semester-scoping | the drill-down's roster widens |

**Proof:** a new test for the semester half — it is untested today.
