## Decisions

rows, then computeCategoryAverages -> computeGeneralRating -> getRemark, the same chain the
detail page (level 0) and the faculty card (level 1) already use.

  rule lives (buildFacultySummary + getRemark). aggregateFacultyResults is refactored to call it,

  department instead of averaging the per-faculty generals; its output SHAPE is unchanged, so the
  top-level page and the export summary CSV need no change and simply show the pooled values.
- features/evaluation-results/evaluation-results.service.ts: getDepartmentSubjectResults also
  returns departmentAggregate (pooled over the department's own rows - it already loads them, so

## Scan

Story: the "Department Summary" widget on app/admin/evaluations/results/[departmentId]/page.tsx
(admin) and app/dean/evaluations/results/[departmentId]/page.tsx (dean) shows a Department Average,
Highest/Lowest Rubric, Overall Sentiment and a "Total Respondents" count. Every one of those is
derived CLIENT-SIDE from the subjects[] array the API already returned, and every one of them is a
mean-of-averages rather than the pooled figure the detail page shows. Tracker: user text only
(repository.md) - story came from the user selecting "Department widget drift".

Path (entry -> caller -> line):

- app/admin/evaluations/results/[departmentId]/page.tsx:70-125  deptMetrics useMemo
  -> reads resultsData.subjects (the array the route returned)
  -> rendered at :263-307 (the Department Summary widget)
- app/dean/evaluations/results/[departmentId]/page.tsx:69-124  the same code, duplicated verbatim
- the API already has every rating row the widget needs:
  features/evaluation-results/evaluation-results.service.ts:75-85 loads ratings + comments for
  every valid eval of the department's faculty

What the widget computes today (client-side, from subjects[]):

  uniqueFaculty     = |distinct facultyId|                                   OK
  totalResp         = SUM(s.totalRespondents)   labelled "Total Respondents" but counts RESPONSES
                                                    (a student who rated 3 subjects counts 3x)
  deptAvg           = mean(s.avgRating)          MEAN OF MEANS (each SUBJECT equal weight)
  deptRemark        = inline copy of the band logic   (3rd copy; canonical = lib/evaluation-utils.ts:40)
  highest / lowest  = mean per rubric column, then max/min   MEAN OF MEANS
  overallSentiment  = mean(s.sentimentScore)     MEAN OF MEANS

The four surfaces that show the same concept, and what each one does today:

  level 0  detail page         (facultySubjectId)  POOLED over that group's rating rows     ACCURATE
  level 1  faculty card        (facultyId)         POOLED over that faculty's rating rows   FIXED (prev story)
  level 2  department widget   (departmentId)      MEAN OF PER-SUBJECT AVERAGES             <- THIS STORY
  level 3  top-level dept card (departmentId)      MEAN OF PER-FACULTY AVERAGES             buildLiveDeptAverages
  level 3' export summary.csv  (departmentId)      same as level 3

So the two department-level surfaces already disagree with EACH OTHER (level 2 vs level 3), and both
disagree with the pooled rule used at levels 0 and 1.

Membership also differs between the two department-level surfaces:
  level 2 = userRepository.listByDepartment(departmentId)          (features/evaluation-results/evaluation-results.service.ts:57)
  level 3 = resolveFacultyDepartment() 4-step fallback chain        (lib/evaluation-utils.ts:214, used by
            features/evaluation-results/evaluation-results.repository.ts:301 listLiveDeptAverages)
            user.departmentId -> faculty_subjects -> sections -> department_courses
A faculty can therefore land in a different department on the two surfaces.

Feasibility notes (no new queries for either level):
- level 2: the service already holds every rating row of the department's evals and every comment's
  sentimentScore, so a pooled department aggregate costs zero extra queries.
- level 3: FacultyDeptInput (lib/evaluation-utils.ts:199) already carries each faculty's raw
  ratings, so buildLiveDeptAverages can pool per department without a new query either.

Proof: none. No test covers deptMetrics or the department widget. Command: npm test

Teach (6=A): why it behaves this way - the widget was written before the API returned anything
faculty-level, so it had only per-subject rows to work with and derived a department figure by
averaging them. The per-subject average is itself a mean of 8 category averages, so averaging
those averages compounds the rounding and weights a 3-response subject equal to a 100-response one.
The department number therefore is not the same KIND of number as the faculty number sitting right
below it, and neither is the same kind as the top-level page's department card. One more thing:
the widget carries its own third copy of the remark bands (getRemarkForAvg was the second, now
deleted), so the band thresholds are duplicated in three places.

BUILD FIX (found by npm run lint): two defects of mine, both caught by tsc.
1. Both department pages used `departmentAggregate` in the JSX but never bound it after the
   deptMetrics useMemo was deleted. Fixed by adding
   `const departmentAggregate = resultsData?.departmentAggregate ?? null` next to `subjects`.
   (The TS7006 "r implicitly any" errors were knock-ons of the unresolved name.)
2. `DepartmentAggregate extends PooledAggregate` inherited a REQUIRED `catColumns` field that
   `aggregateDepartmentResults`'s object literal does not provide, so TS flagged the eight
   named rubric columns as excess properties. Fixed by declaring DepartmentAggregate standalone
   (same shape the literal actually produces, mirroring FacultyAggregate's standalone style)
   instead of extending PooledAggregate.
   NOTE for the future: PooledAggregate is the shape of aggregatePooledResults' return (it has
   catColumns as a record); FacultyAggregate and DepartmentAggregate are the CONCRETE shapes
   (eight named columns) and must not extend it.
