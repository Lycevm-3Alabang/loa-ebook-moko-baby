## Decisions

### D1 — the fixes copy the model the repo already has

`features/evaluations/evaluations.repository.ts` already contains the fixed pattern, twice over:
`listSubmittedByPeriodAndEvaluatees` (chunked `.in()` + a `.range()` page loop) and
`countSubmittedByFacultySubjectIds` (chunked + paged). The file already has the two constants
(`IN_CHUNK_SIZE = 100`, `PAGE_SIZE = 1000`) and the `chunkStrIds` helper. **The fix is to apply the
file's own model to the two reads that do not have it** — no new idea, no new helper.

### D2 — the order must be total, and one of them keeps its visible order

A page loop needs a **total** order, or a row can be skipped or duplicated at a page boundary.

- **Read 1** (`listSubmittedByPeriodAndFacultySubjectIds`) orders by `submittedAt` today. Paging
  on `submittedAt` alone is **not** total (ties, and NULLs). The fix orders by
  **`(submittedAt, id)`** — `id` is the primary key, so the pair is total, and the **visible row
  order is unchanged** (the two faculty-detail routes render the responses in this order).
- **Read 2** (`listStatusByPeriodAndFacultySubjectIds`) has **no order at all** today, so the rows
  come back in an arbitrary order. The fix orders by `id` — a total order, and the callers
  (`evaluation-status.service.ts:95`, `:170`) aggregate, so the order is not visible.
- **Read 3** (the student-breakdown's evaluations) has no order either; the fix orders by `id`.
  The breakdown is **anonymous** (`S1`, `S2`, … — the dean route renumbers the rows), so the order
  is not semantic — it only becomes deterministic.

### D3 — the comments read is chunked, and the chunk size also settles the row cap

`getStudentBreakdownsForFaculties` reads the comments with one `.in("evaluationId", allEvalIds)`.
The fix chunks it at **100** ids, the same size `listCommentScores` uses — and that size is also
what keeps the **row** cap out: a chunk of 100 evaluation ids holds at most a few hundred
comments, so a chunk comes back in a single request (the same reasoning as
`lib/db/common.ts`'s `RATINGS_IN_CHUNK_SIZE`).

### D4 — the ratings read is already safe

`fetchRatingsWithCategories` chunks at 37 evaluations (999 rating rows = one page) and pages each
chunk. **Nothing to do there** — Lesson 7b's corollary, already applied.

## Notes for the implementer

- The page loop calls `supabase.from()` **inside** the loop (a real client advances the offset in
  the `Range` header, not on the chain) — the test model in the file already assumes this.
- `PAGE_SIZE` is 1,000 and the cap is 1,000: a full page is never a truncated one, so the loop's
  contract holds. If the cap ever moves, the page size moves with it.
