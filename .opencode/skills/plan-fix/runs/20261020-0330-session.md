All 7 slices applied. The change set: 31 files, +298 / -666 - a net removal of 368 lines.

evaluation_results is now EXACTLY a visibility grouping. Every remaining read/write of it is a
flag: setVisibility's existence lookup, the flag update, the flag insert, getVisibilityMap, the

  features/evaluations/evaluations.repository.ts inside findPending - so it is untouched. (I had
  told the user the opposite mid-story; corrected in S5.)

UNIQUE("semesterId","facultyId") stay as they are. The table's rows are a MIX: the legacy cached
rows ARE the visibility rows (one per period+faculty), carrying the flag with the stale scores

## Decisions

USER DECISION (verbatim): "then we can use evaluation_results only for is_results_visible, deprecate
all that refers to its other columns score" and "it's just a visibility grouping".

D1 = A. The report service gets a NEW live per-faculty source with the SAME row shape it reads
today: evaluationResultRepository.listLiveFacultyResults(periodId) -> { facultyId,
totalRespondents, generalRating, the 8 category columns }. It shares the context loader the
membership story already extracted, so there is no duplication.
D2 = A. supabase-schema.sql is NOT touched. The app stops reading and writing the score columns;
the table keeps its shape and its existing rows. No migration, no fresh-install risk.
D3 = A. Both diagnostic surfaces point at the visibility rows.
  - the semester impacts panel counts the RELEASED flags for the semester (is_results_visible = true)
    and the label becomes "Released Results" (the table's rows are a MIX - the legacy cached rows
    ARE the visibility rows, one per (period, faculty), with the score columns still populated
    from the last compute; counting only the flags that are ON is the honest number).
  - the admin user related-data view lists the visibility columns only
    (facultyId, evaluation_period_id, semesterId, is_results_visible) under the key
    "evaluation_visibility" -> the panel's auto-derived label becomes "Evaluation Visibility".
D4 = A. The recompute workflow is retired. Its burst coalescing was clocked by the cached
computedAt - a clock that disappears with the cache - and a new submission cannot create a stale
evaluation, while the dashboards now compute live. The janitor is called directly where staleness
CAN arise: faculty-subject reassign, student-enrollment change, both invalidate routes, the
disabled-restore route, the faculty import.

FOUND WHILE SCANNING (not in the original inventory): the DEAN's top-level route
(app/api/dean/evaluation-results/route.ts) is a real consumer of the score columns, and it
computes the department average as a MEAN OF THE PER-FACULTY GENERALS (lines 125-127) - the same
mean-of-means the drift story just removed from the admin side. The admin and dean top-level
pages therefore disagree about the SAME department today. Re-pointing the dean's route at
listLiveDeptAverages (pooled, like the admin route) fixes both the cached dependency and the
disagreement in one move.

INVARIANTS PRESERVED
- API routes stay thin: every replacement is a repository method; the routes only call them. The
  report service currently reaches around the repository with a direct supabase read
  (evaluation-report.service.ts:79, 230) - the re-point removes that.
- All Supabase access via repositories/DI: the re-point goes through the repository; no new direct
  supabase in any service or route.
- proxy.ts access enforcement: untouched. Role pipe-delimited priority: n/a.
- Double-click via SubmitButton: n/a - read-only reports.
