## Decisions

Scope: Option A - the department results page only, both tabs:
  - the "By Subject & Section" table gets a Section column
  - the "By Faculty" card's expanded per-subject rows get a Section column (a faculty teaching
    the same subject in two sections has two rows there too - that is where the ambiguity bites)
  - admin AND dean pages.
NOT in scope: the detail page header, the export CSVs, the PDFs, the top-level results page.

Format: Option A - PROGRAM-NAME (e.g. "BSCS-1A"), the format the student evaluations view and
the faculty-enroll page already use.

WHAT CHANGES
- features/evaluation-results/evaluation-results.service.ts: resolve each row's section and add
  sectionProgram / sectionName to DepartmentSubjectResult. The section_id is ALREADY in the
  service's hands (facultySubjectRepository.findByIds does select("*")). The only new data is the
  section's name+program: one query via sectionRepository.list(), resolved in memory - the house
  pattern from app/api/student/evaluations/bootstrap/route.ts:100-121 ("sections are few, so
  resolve in memory from the row's OWN section").
- app/api/dean/evaluation-results/departments/[departmentId]/route.ts: the dean's inlined copy of
  the same rows. It is typed DepartmentSubjectResult[], so it must be updated WITH the service.
- features/evaluations/components/DepartmentSubjectView.tsx: a Section column in both tables. The
  label is composed ONCE, in a two-line helper (sectionProgram-sectionName, falling back to the
  name alone), used by both tables. The search also matches the section label.
- app/admin|app/dean/evaluations/results/[departmentId]/page.tsx: the local SubjectRow interfaces
  gain the two fields.

FIELD NAMES: sectionProgram + sectionName, matching what the student bootstrap route already
returns, so the same section reads the same way on every surface.

INVARIANTS PRESERVED
- API routes stay thin: the section is resolved in the SERVICE (as the student bootstrap route
  does), not in the route or the page. The routes and the response shape are otherwise untouched.
- All Supabase access via repositories/DI: sectionRepository.list() through the factory; no direct
  supabase in the service or the page; no new query beyond that one.
- proxy.ts access enforcement: untouched. Role pipe-delimited priority: n/a.
- Double-click via SubmitButton: n/a, read-only view.

LAYERING: lib/types (row shape) -> features/evaluation-results/evaluation-results.service.ts
(resolve the section) -> app/api/... routes (unchanged shape) -> features/evaluations/components/
DepartmentSubjectView.tsx (render) -> app/.../page.tsx (the local SubjectRow type).

GOLD PATHS TO READ FIRST: app/api/, features/, lib/repositories/factory.ts, lib/auth.ts, proxy.ts
(named in repository.md Gold paths). Also app/api/student/evaluations/bootstrap/route.ts (the
house section-resolution pattern) and lib/types/evaluation.ts (SectionData, ISectionRepository).

PROOF COMMAND: npm test (npx vitest run). Final: npm run lint + npm run build.

BLAST RADIUS: the department results rows gain two nullable fields - additive, so any consumer
that ignores them is unaffected (the only consumers are the two pages and the component). One
extra query per department page view (sections are few, and the same query the student bootstrap

Proof: none for the section column. Command: npm test

Teach (6=A): why it behaves this way - a faculty_subject row is the TEACHING ASSIGNMENT, not the
subject: (faculty, subject, section, semester). Two assignments can share a subject and differ
only by section - two different class groups, two different sets of students, two different
evaluation sets. The tab was named for that ("By Subject & Section"), but the table only ever
showed the subject, so two rows for the same subject looked like a duplicate rather than two
classes. The student-facing view already solves this (it shows program-name); the admin report
never got the same treatment. Why it matters: a reader cannot tell which class group a rating
belongs to, and cannot tell two rows apart at all. When it bites: any faculty who teaches the
same subject in more than one section - common in smaller programs.

  test's row helper was updated so it still compiles.
